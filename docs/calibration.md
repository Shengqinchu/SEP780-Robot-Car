# 电池到货后的校准

[English](calibration.en.md) | [返回 README](../README.md)

按顺序完成下列步骤。一次只改一个参数，每次测试记录固件提交、参数、场地和现象。准备直尺、浅色测试板、套件黑胶带，以及能架空四轮的稳固支撑。

## 1. 建立原厂硬件基线

先按[装配与上电检查](bring-up.md)核对电池极性、插头和开关。断电插拔线材，上传前移除蓝牙。首次通电架空四轮，留出超声波转头活动空间，确保能随时关闭车上电源。

1. 上传原厂 `servo_center`，实际观察归中，断电后固定转头朝正前。
2. 优先上传项目的 `motor_check`，架空四轮确认正向是否一致。它上电等待 3 秒，仅按原厂基线 PWM 200 前进 1 秒，然后永久停止；不读取超声波或其他传感器。原厂 `motor_test` 会自动重复动作，只作为后续故障定位参考。
3. 用 `tracking_sensor` 检查三路黑线/浅色底读数；左、中、右分别遮盖，不仅检查组合值。
4. 用原厂 `ultrasonic_test` 检查测距，该示例会扫动舵机。摆放平整、能反射声波的目标。

原厂读数异常时先处理接线、供电、安装位置，再上传项目固件。不要同时改软件算法来补偿未确认的接线问题。

如果 `servo_center` 上电后没有可见动作，可能原本就在中位，不能据此判断通过或故障。可在重新确认接线、供电状态和串口后上传项目诊断程序 [`servo_check`](../firmware/servo_check/servo_check.ino)：电机 PWM 引脚保持低电平，每次启动/复位只围绕源码中注明的候选中点小幅摆动一轮，约 7.5 秒后保持该中点。上传时断开电池供电；测试时先拔 USB，再在开关关闭时接回上层板电池插头，架空四轮、留足转头空间后上电观察约 8 秒并关电。串口打印的是命令角度，不是实际角度反馈；打开串口也可能复位并重复动作。有卡住嗡响、持续抖动、发热或非预期车轮运动时立即断电，不用手硬掰舵机。

`motor_check` 同样会在每次上电或复位时自动执行一次。上传时必须关闭两个开关、断开电池圆形供电，只接下层 USB-C；测试时拔掉 USB，四轮稳固架空且周围无手、衣物和线缆后，再接回电池并打开两个开关。看到 3 秒等待后的 1 秒转动即关电，记录四轮是否都转且车底接地点方向是否一致。该诊断会临时覆盖正式固件，完成后必须重新上传 `robot_car`。

本车首次按原厂正向极性实测时，四轮在 PWM 200 下能够启动，但车轮最上沿朝车尾移动，实际为倒车。因此正式固件已同时启用左右电机反转，诊断程序也使用相同的校准极性；这属于本车接线/安装适配，不修改原厂快照。

检查 SERVO 接头时，不能只看三色线顺序：必须逐根确认 `SIG[2]`、`5V`、`GND` 三根针都进入对应插孔，特别留意最外侧的信号针是否被漏在插头外。实际调试曾出现信号针悬空、板灯正常但舵机完全不动，断电重新插好后恢复动作。

能够转动但最终朝向偏斜时，先把舵盘安装到最接近正前的齿位。齿位无法精确对中时，再用小幅软件偏置补齐；原厂校准功能将偏置限制在约 `-10..+10` 度。首轮 `+8` 度（中点 `98` 度）实车测试扩大了偏差，反向 `-8` 度（中点 `82` 度）后实物照片显示转头已基本沿车身中线朝前，因此项目暂定 `82` 度为中点；诊断程序只在其两侧各摆动 `5` 度。完全断电后安装输出轴中央的原配最小固定螺丝。不要靠手硬扳输出轴、用大幅软件偏置掩盖错误齿位，或拆舵机外壳。视觉归中不代替测距验收；还需用正前方平面目标验证超声波读数。

## 2. 上传项目固件

`robot_car` 启动会将舵机转到配置的中位，但不会自动启动车轮。轮子继续架空，先确认转头不会顶住结构。关闭车板 POWER 后按原厂流程上传，完成后再接入正确的电池供电并开启车板。

```powershell
./scripts/List-Boards.ps1
$port = Read-Host '输入刚确认的小车串口'
./scripts/Upload.ps1 -Program robot_car -Port $port -ConfirmHardwareReady
./scripts/Robot.ps1 -Action observe -Port $port -Seconds 10 -ConfirmHardwareReady
```

`observe` 不发送指令。它记录 `line`、`range_mm`、`battery_mv`、当前模式和左右轮 PWM。打开串口可能复位主控，因此即使只观察也要留出舵机活动空间。不要与 IDE 串口监视器同时占用端口。

## 3. 校准读数和方向

参数集中在 [config.h](../firmware/robot_car/config.h)。修改后重新编译、测试并显式上传。

| 项目 | 方法 | 修改位置 |
| --- | --- | --- |
| 舵机中位 | 确认标称 90 度时超声波朝正前，优先调整舵盘安装 | `hardware::servo_center_degrees` |
| 电池电压 | 将遥测与万用表电池端电压比较；偏差明显先检查接线与分压 | `hardware::adc_full_scale_mv`，默认 20000 |
| 黑白极性 | 官方默认黑线为 1；分别验证三路 | `hardware::black_reads_high` |
| 左右电机方向 | 在架空状态短时间驱动，确认左右逻辑正值均为前进 | `hardware::invert_left_motor` / `invert_right_motor` |
| 左右轮偏差 | 低速短直线，多次观察偏向，再小幅调整 | `left_trim_pwm` / `right_trim_pwm` |

前方需有约 30 cm 到 4 m 范围内的有效回波才允许启动。没有回波时 `range_mm=0`，程序会停车，不把它当作“前方无限远”。电池默认工作检查范围为 6.6 V 到 9.0 V；ARM 前低压立即拒绝，运行中连续低压 300 ms 才停车，避免把启动浪涌的一次 ADC 瞬态当成耗尽。它仍只是软件检查，不代替电芯保护或充电器。

先发送 1 秒、低 PWM 的架空动作：

```powershell
./scripts/Robot.ps1 -Action drive -Port $port -Left 70 -Right 70 -Seconds 1 -ConfirmHardwareReady -ConfirmMotionClear
./scripts/Robot.ps1 -Action stop -Port $port -ConfirmHardwareReady
```

输出太小导致轮子不动时，先核对电池、插头和电机方向，再逐步调整。首次地面测试同样从低速、短时间开始。

## 4. 调整循迹与遇障行为

在哑光白色平面贴单条哑光黑线，先直线，再增加宽缓弯道，避免阳光直射循迹传感器。木色地板、明显木纹或高光表面不是稳定基准：若场地不能更换，先铺白色海报纸、泡沫板或足够宽的白色胶带，再在中央贴黑线。标准静止读数应为：全白 `000`，只有中间探头压黑线为 `010`，只有左/右探头压黑线分别为 `100`/`001`。如果木地板与黑线给出相同二值，软件仅凭当前三路数字输入无法恢复对比度，应更换背景或另做模拟量/传感器硬件升级。

| 参数 | 初始值 | 校准重点 |
| --- | --- | --- |
| `cruise_pwm` | 100 | 固件兼容命令的默认值；新 App 遥控不使用它作为摇杆上限 |
| `min_runtime_pwm` | 50 | 固件兼容范围下限；实车观察已确认 50–100 不能可靠起步，App 因此从 110 开始 |
| `line_pulse_pwm` | 120 | 步进档及正常档中线直行的固定幅值；不受 App 手动上限影响 |
| `line_turn_pwm` | 150 | 正常档侧偏与单侧位的连续转弯幅值；不提高直线速度 |
| `line_pulse_on_ms` / `line_pulse_off_ms` | 80 / 80 | 先驱动再零 PWM 滑行；必须在固定白底黑线路线上验收转弯和惯性 |
| `turn_reduction_pwm` | 120 | 正常档在 `110/011` 时内轮归零；`100/001` 会进一步让内轮反转 |
| `max_pwm` | 200 | 固件协议上限；电机 I/O 实际截断到 180，App 可选上限也为 180；PWM 不是实际速度单位 |
| `obstacle_stop_mm` | 200 | 加上测距误差和实际滑行距离后仍能停在目标前 |
| `obstacle_resume_mm` | 300 | 大于停车阈值，避免边缘反复启停 |
| `clear_hold_ms` | 600 | 需连续清晰回波并至少有三次不同采样才能恢复 |

使用红外遥控器：`1` 启动循迹，`0` 或电源键停车。手动先按 `2`，按住方向键移动；释放后手动指令在默认 350 ms 后过期。切换模式先停车。

App 的“步进 / 正常”选择不同的循迹输出策略。步进不用 `delay()`，所有有效线型均按 PWM 120 驱动 80 ms / 滑行 80 ms。正常档在 `010` 中线时保留同样节奏，避免直线冲出；在 `110/011` 时以 PWM 150 连续单侧转，在 `100/001` 时以 `-150/150` 或 `150/-150` 原地修正。两档遇到障碍、`000/101/111`、STOP、低压或传感器故障都会立即归零，且不会在脱线后盲目搜线。切换档位会先停车，红外 `1` 始终使用步进。

新 App 的赛车摇杆只控制手动模式：可选速度上限为 110–180，默认 150；拖动量和方向经死区、响应曲线、左右轮差速混合与加减速限制后，每 50 ms 最多发送一帧。松手必须立即回到 `0/0`。架空验收时依次测试小幅前进、全前进、左右弧线、原地转向、后退和前后反转，确认遥测中的左右请求与实体方向一致，再落地短测。长按“鸣笛”应发出重复短响，松手、STOP 或断连应停止；蜂鸣器与电池采样共用 A0，因此还要确认鸣笛期间遥测仍周期更新且无异常低压锁定。

2026-09-21 的同路线 A/B 已完成：步进在侧向位周期动作但无法克服急弯负载；全连续模式直线过快，直接冲出黑线。这排除了“只把整段改成连续”作为最终方案，并促成正常混合档。随后架空观察显示，PWM 120 的反向轮组从静止不可靠，先以中线直行再切到单侧位则能动作；这更符合反向冷启动扭矩不足，而不是已经证明某一侧电机损坏。原厂循迹转弯最高使用约 `160/-140`，本项目此前 PWM 150 双向电机测试已通过，因此当前刷入版只把正常档转弯设为 150。下一轮仍从相同起点测试：中线应保持步进，侧偏应连续转动，单侧位应原地修正；如果它转向相反，立即停止并核对 App 三位遥测和物理左右。若进入 `000/101/111`，控制器应停车，不靠盲转掩盖场地或传感器覆盖问题。一次只改一个参数，并在最终方案固定后保存五次相同路线结果。

主控板内置 `L` 指示灯在控制模式确实进入后常亮，停车或启动被拒绝时熄灭。接收板自身的闪灯只表示看到了红外信号，不能代替这一状态判断。

电脑控制采用限时会话：

```powershell
./scripts/Robot.ps1 -Action line -Port $port -Seconds 5 -ConfirmHardwareReady -ConfirmMotionClear
```

电脑会话结束或发生错误时发送 STOP。打开串口可能复位主控，因此运动会话会在发送 ARM 前等待最多 3 秒，直到收到首个 `20..4000 mm` 有效测距；超时则不启动并保存失败记录。电脑断开后，串口拥有的循迹模式由 1200 ms 指令超时停止。红外启动的循迹可脱离电脑持续运行。地面运动不要拖拽或缠绕 USB 线，独立运行优先使用红外遥控。

这版只做前方障碍停车与恢复，不规划绕行。手动模式在前方障碍内阻止净前向运动，但保留倒车和原地转向供操作者脱离；没有后方/侧方传感器，因此倒车必须由操作者观察环境。停止是将 PWM 设为 0，不是保证机械上瞬间刹停。

## 5. 记录和复测

按[验证清单](test-plan.md)每项至少重复五次，记录成功次数、失败条件、距离和是否发生异常复位。未执行的项目留空或写“未执行”。

原始记录保存到 `artifacts/local/robot-*.jsonl`。选定一次会话后导出 CSV：

```powershell
. ./scripts/Common.ps1
$trace = Read-Host '输入要导出的 robot JSONL 路径'
& (Get-HostPython) -X utf8 ./host/export_telemetry.py $trace ./artifacts/local/calibration.csv
```

使用[实测记录模板](templates/hardware-test.md)整理一次测试，再将真实发现与参数修改追加到 [DEVLOG.md](../DEVLOG.md)。固定最终参数后重复相同路线，比较原厂与项目固件。
